NGS Workshop Deployment Review

2 November 2026Commit 926907d7 scripts & docs, 13 data files revieweddovm (do-vm-manager) reviewed

The repo provisions one DigitalOcean VM per participant and walks them through a 16-step CLI pipeline. It works, but setup is slow, fragile to re-run, depends on a shared NFS server, and is now out of sync with the new hg38 OncoSpan dataset. The dovm droplet manager plus a single pre-built snapshot solves most of the setup side. Below: what exists, what breaks, and a plan that gets every participant from FASTQ to a signed-out clinical report.

What needs attention first

Licence

Licensed ANNOVAR link is public

configure_vm.sh:17 contains a personal ANNOVAR download token, and ANNOVAR's licence forbids redistribution. Ask for a new link and keep it out of git. Switching to VEP removes the problem.

High

Genome build mismatch

The new FASTQ/BAM/BED/truth VCF are hg38 (chr-prefixed, bwa-mem2 hg38). The participant guide still aligns to human_g1k_v37 and annotates with hg19.

High

Retire the NFS server

Every VM reads a ~5 GB bwa index from one NFS server at the same moment in step 5. Baking assets into a snapshot removes the server and the bottleneck.

Medium

Setup is slow and fragile

Two VMs at a time over interactive SSH, no error checking, unpinned tools, and a retired Mambaforge installer. dovm and a snapshot replace all of it.

For instructors: provisioning with dovm

dovm (do-vm-manager) already does most of what this course needs. It creates droplets from a YAML spec in batches of 10, can be re-run safely, tags everything it owns, and writes IP lists and an Ansible inventory. Combined with one pre-built snapshot, it replaces create_vm.py, create_user.sh, prepare_vm.sh, the ssh-keyscan step and the NFS server.

Snapshot size: what DigitalOcean's docs say

DigitalOcean does not document a maximum size for Droplet snapshots, and no limit on how many droplets can be created from one. The size limits you may have run into last time are these:

  • Disk must be at least the source disk. "You must select a disk size equal to or larger than the Droplet used to create the snapshot." A snapshot taken from a 240 GB droplet cannot create a 160 GB one, and you cannot shrink it afterwards.
  • 100 GB applies to custom images, not snapshots. Uploaded images "must be less than 100 GB uncompressed." Snapshots taken from a droplet are not uploaded images, so this cap does not apply to them.
  • Datacenter capacity. A snapshot stored in a limited-capacity datacenter cannot create droplets there. The fix is to transfer the snapshot to another region.

Snapshots cost $0.06 per GB per month. A course-year image of roughly 30–40 GB costs about $2–3 a month to keep.

Rules that avoid the disk-size trap: build the prep VM on the smallest disk that holds the assets, and use the same or a larger disk for the student VMs. Never resize the prep VM's disk upward, because that permanently raises the snapshot's minimum disk size. Check before class with doctl compute snapshot get <id> --format Name,MinDiskSize,Regions.

What goes in the image

Do not create the bioseq user in the snapshot. dovm's cloud-init creates it at first boot, and useradd copies /etc/skel into the new home directory. So the image keeps shared files in system locations:

/etc/profile.d/ngs.sh            activates it at login, sets REF, BED, VEP_CACHE
/opt/assets/hg38/                FASTA, .fai, .dict, bwa index
/opt/assets/vep/                 VEP cache (or ANNOVAR humandb)

The --login-user account has no sudo. The participant guide never needs it, because everything is installed in the image.

For participants: see every transformation

The current guide is a good list of commands. The goal is for participants to understand what each command does to the data. Three changes would help most: remove access friction, show each file after every step, and end with a real report built from their own calls.

Remove access friction

  • Serve code-server or JupyterLab over HTTPS (Caddy + a per-VM hostname). Participants get a terminal, a file browser, and an HTML viewer in one browser tab. That removes the separate Windows/macOS scp steps (4 and 16).
  • Host igv.js on the VM, preloaded with hg38 and the participant's BAM, so they can inspect KRAS G12D reads without downloading anything.
  • Keep SSH as an option for people who want the real terminal experience.

Make the pipeline teachable

  • Start with source ~/workshop.env that sets SAMPLE, REF, BED, THREADS. Commands become shorter and typo-resistant.
  • After every step, a check-step N command confirms the expected output exists and looks right, with a plain explanation of any failure.
  • A catch-up N command copies precomputed outputs, so nobody gets stuck behind a typo.
  • Finish by running the whole pipeline again as a single Snakemake or make call to show what automation buys you.

Close with a clinical report

Add a make_report.py (Jinja2 → HTML, optional PDF) that reads the participant's own outputs and builds a molecular pathology–style report. Have participants assign tiers to three or four variants before running it, then compare their calls with the generated report.

  • Header: synthetic patient and specimen IDs, assay name, genome build, pipeline versions from the lock file
  • QC: reads, % Q30 (fastp JSON), duplicate rate, mean and minimum target depth (mosdepth), % targets ≥ 250×
  • Results: variants grouped by AMP/ASCO/CAP tier with gene, HGVSc, HGVSp, VAF, depth, ClinVar
  • Methods: generated from the actual commands run (@PG lines in the BAM header provide this)
  • Limitations: 5% VAF cutoff, regions not covered (FLT3), no CNV or fusion detection
  • Truth comparison (teaching appendix): sensitivity and PPV against OncoSpan
Annotation choice. The prep folder already holds VEP output with MANE and ACMG fields, so Ensembl VEP with an offline hg38 cache plus a recent ClinVar VCF fits best. It is free to redistribute, which also removes the ANNOVAR licence problem. snpEff is a lighter alternative if image size matters more than MANE transcript selection.
