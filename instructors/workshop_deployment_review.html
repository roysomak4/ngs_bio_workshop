NGS Workshop Deployment Review

Revised 3 November 2026 (first issued 2 November)Commit 9ebe4d1Pipeline from bioinformatics_pipeline_and_software_list.mddovm (do-vm-manager) reviewed

The repo provisions one DigitalOcean VM per participant and walks them through a CLI pipeline. Setup is slow, fragile to re-run and depends on a shared NFS server, and the participant guide is out of sync with the 2026 hg38 dataset and tool list. The 2026 session runs three variant-calling rounds against a known truth set: VarScan at 5% VAF, VarScan at a lower cutoff, then VarDict for the FLT3 ITD, each annotated with fastVEP and reviewed in IGV. The dovm droplet manager plus a single pre-built snapshot covers the setup side.

Why each round misses what it misses

  • Round 1: the 5% cutoff filters out the 3% and 4% calls by design. BRAF V600E at 6% sits right at the edge and may drop out depending on depth.
  • Round 2: lowering the cutoff recovers those calls but lets in more noise. The benchmark's FP count shows the trade-off.
  • Round 3: no VarScan setting finds the FLT3 ITD. The 279 bp insertion is about twice the read length, so bwa soft-clips the reads instead of writing an insertion, and mpileup never sees one. VarDict assembles the soft-clipped reads into the ITD. The truth record's VD/AF/RD/ALD FORMAT fields look like VarDict output (AF 6.1% observed vs 8.25% expected), which suggests this has already been shown to work on this data.

Two small wrappers keep the rounds consistent

  • annotate-vcf runs fastvep annotate twice with the image's GFF3, FASTA and ClinVar database: once for a VCF with a CSQ field, once for a table with gene symbols (--symbol --output-format tab). It prints each fastvep command before running it, so participants still see the real tool call.
  • benchmark-vcf left-normalises the calls and the truth VCF with bcftools norm, then prints found/missed with expected and observed VAF for each truth variant, plus the false positives inside the targets. The FLT3 ITD is matched by position window, not exact allele: callers place a long insertion slightly differently, and an exact match would wrongly score it as missed. Given all three rounds and --html ~/work/qc/benchmark.html, it also writes a self-contained report comparing them side by side (summary cards, per-variant found/missed with a NEW marker, false positives), with each position linking to the portal's IGV page.

Snapshot size: what DigitalOcean's docs say

DigitalOcean does not document a maximum size for Droplet snapshots, and no limit on how many droplets can be created from one. The size limits you may have run into last time are these:

  • Disk must be at least the source disk. "You must select a disk size equal to or larger than the Droplet used to create the snapshot." A snapshot taken from a 240 GB droplet cannot create a 160 GB one, and you cannot shrink it afterwards.
  • 100 GB applies to custom images, not snapshots. Uploaded images "must be less than 100 GB uncompressed." Snapshots taken from a droplet are not uploaded images, so this cap does not apply to them.
  • Datacenter capacity. A snapshot stored in a limited-capacity datacenter cannot create droplets there. The fix is to transfer the snapshot to another region.

Snapshots cost $0.06 per GB per month. A course-year image of roughly 30–40 GB costs about $2–3 a month to keep. Measure the fastVEP annotation data on the prep VM before settling on a disk size.

Rules that avoid the disk-size trap: build the prep VM on the smallest disk that holds the assets, and use the same or a larger disk for the student VMs. Never resize the prep VM's disk upward, because that permanently raises the snapshot's minimum disk size. Check before class with doctl compute snapshot get <id> --format Name,MinDiskSize,Regions.

What goes in the image

Do not create the bioseq user in the snapshot. dovm's cloud-init creates it at first boot, and useradd copies /etc/skel into the new home directory. So the image keeps shared files in system locations:

The --login-user account has no sudo. The participant guide never needs it, because everything is installed in the image.

Uploading the indexed reference. Copy it to the prep VM before running the build playbook; rsync --partial resumes if the upload drops. Before taking the snapshot, check three things. First, contig names are chr-prefixed, so they match the BED and truth VCF. Second, the bwa index was built from this exact FASTA (.amb .ann .bwt .pac .sa sit next to it with the same prefix). Third, if the FASTA contains ALT contigs, the matching .alt file is present; otherwise reads in ALT-covered regions get MAPQ 0. A no-alt analysis set avoids that issue.

For participants: see every transformation

The 2026 session is built around comparison: the same BAM, three calling strategies, and a truth set to score each one. Participants learn the most when they can see each file change and when nobody gets stuck on a typo.

Commands in a terminal, viewing in a browser

  • Run every step in a real shell. Participants SSH in (ssh bioseq@<ip>; built into macOS, Linux and Windows 10/11) and paste each command from the guide. No IDE, no notebook, so nothing hides what the tools do.
  • Look at results in the browser. A small web portal on each VM at http://<ip>/ shows the HTML reports and an IGV page. Both read files straight from ~/work, so a report or BAM is viewable the moment the command finishes. No scp, no desktop IGV install.

Make the pipeline teachable

  • Start with source ~/workshop.env that sets SAMPLE, R1, R2, REF, BED, TRUTH, THREADS. Commands become shorter and typo-resistant.
  • After every step, a check-step N command confirms the expected output exists and looks right, with a plain explanation of any failure.
  • A catch-up N command copies precomputed outputs, so nobody gets stuck behind a typo. This matters most before round 1, since rounds 2 and 3 reuse the same BAM.
  • Keep a shared table on screen of each round's TP/FN/FP so the class sees the trend together.
